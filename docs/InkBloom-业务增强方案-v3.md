## 0. 一句话结论

> **InkBloom 已经把"作者侧的生产工具"做完了，但产品只做了一半——读者侧为零。**  
> 下一阶段的全部业务增量，来自把「导出即终点」的孤岛，改造成「创作 → 发布 → 阅读 → 互动 → 反哺创作」的闭环。这既是《备忘录》里那条被搁置的初心，也是唯一不靠买量就能转起来的增长飞轮。

## 2. 三个结构性判断

### 判断一：产品只做了一半，读者侧完全空白

《备忘录》的产品原点是：

> 不仅是编辑器，还是小说阅读器：交互式微创作的小说阅读体验，低消耗的小说微调玩法

对照代码：三件套里只有「编辑器」落地，「阅读器」与「交互式微创作」一行未做。当前作者写完 → 导出 md/html → 自己去公众号/知乎/起点发布，平台在此处**彻底退出链路**。

后果是三重的：

1. **没有自然获客**——作品不产生外链、不被搜索引擎索引、不在社交网络传播，增长只能靠买量；
2. **没有反馈闭环**——作者不知道读者在哪一段弃书、哪一句被划线、哪个角色被喜欢，AI 也拿不到偏好信号；
3. **没有留存抓手**——工具型产品天然是"用完即走"，用户一旦在别处发布，InkBloom 就退化成一个可以轻易替换的编辑器。

### 判断二：AI 是"按钮集合"，不是"创作伙伴"

现有 14 个 AI 端点全部是同一种范式：**选中文本 → 点动作 → 出结果 → 结束**。无状态、无记忆、无主动介入。

用户感知是"一个更聪明的同义词替换器"，这直接决定了两件事：

- **付费意愿天花板低**：润色/扩写这类能力，用户会拿它跟免费的大模型对话框比，凭什么付 9.9 元？
- **可被轻易替代**：任何支持长上下文的模型 + 一个粘贴动作就能复现 80% 的效果。

真正的壁垒不在"能不能续写"，而在"**它懂不懂我这本书**"——谁在哪儿、埋过什么伏笔、哪个角色已经知道了什么、我的句子有多长。这恰恰是现有 `novel_memory` + `knowledge_nodes` + `novel_outline` 三份数据已经躺在库里、却彼此不通、也没被 AI 充分利用的资产。

### 判断三：商业化只建了收费管道，没建增长引擎

现有模型：**订阅 10 元/月卖基础设施（云同步）+ Token 包卖 AI 算力**。按方案 5.5 的粗算，万级注册规模下月收入约 1.6 万元。

问题在于这个模型的两个乘数都起不来：

- **客单价上不去**：10 元/月打穿的是码字工具年费带，但"云同步"这个权益对单机创作者是弱需求，提价没有支撑；
- **获客成本降不下来**：没有 UGC 传播、没有协作带来的团队扩散、没有内容分发的 SEO 长尾，全部依赖外部流量，单位经济模型跑不通。

解法不是调价，是**换权益结构**：把订阅从"卖存储"改成"卖留存与增长"（版本历史 + 发布 + 读者数据），把 AI 从"卖算力"改成"卖深度"（伏笔追踪 + 风格一致性 + 数字孪生）。

## 3. 战略定位重述

### 3.1 定位升级

|      | 现在                    | 升级后                            |
| ---- | --------------------- | ------------------------------ |
| 一句话  | 面向自媒体创作者的 AIGC 图文创作工具 | **AI 原生的故事工作台：创作 × 阅读 × 分发一体** |
| 用户视角 | 我在这写，写完好去别处发          | **我在这写，写完就有人读，读的人还能陪我一起写**     |
| 竞争维度 | 编辑器体验、AI 动作数量         | **作品理解深度 + 读者连接**              |
| 护城河  | 功能堆叠（易被复制）            | 作品数字资产 + 读者关系（越用越深）            |

### 3.2 三端模型

```
         ┌──────────────── 作者端（已有，增强）────────────────┐
         │  编辑器 · 大纲 · 记忆 · 知识图谱 · 版本历史 · AI 伙伴 │
         └───────────────────────┬───────────────────────────┘
                                 │ 一键发布（E4）
                                 ▼
         ┌──────────────── 分发层（新增）────────────────────┐
         │  作品主页 H5 · SEO/OG 卡片 · 章节定时发布 · 分享   │
         └───────────────────────┬───────────────────────────┘
                                 │
                                 ▼
         ┌──────────────── 读者端（新增）────────────────────┐
         │  沉浸式阅读器 · 追更 · 段落互动 · 二创投稿 · 打赏   │
         └───────────────────────┬───────────────────────────┘
                                 │
              互动数据 / 采纳回流 ──┘──► 反哺 AI（E3）+ 作者仪表盘
```

飞轮：**作者发布 → 读者阅读互动 → 互动数据提升 AI 质量 + 给作者正反馈 → 作者留存并产出更多 → 读者转作者 → 拉新**。

## 4. 增强方案（E1–E7）

> 每个增强项均给出：现状 → 缺口 → 方案 → 涉及模块 → 商业价值 → 验收指标。



---

### E1 · 版本历史与时间机器（P0 · 信任基建）

**优先级最高，且是其他一切的前提。**

**现状**：`DiffViewer` 组件已存在，但只用于 AI 改写的即时对比，不留痕。整本作品没有任何历史版本，AI 改写一旦点"接受"就不可逆。

**缺口（K2）**：在一个高频使用 AI 改写的产品里没有版本历史，等于要求用户每次改写前手动复制原文。这是留存的基础设施，不是锦上添花。

**方案**：

| 能力        | 说明                                                                        |
| --------- | ------------------------------------------------------------------------- |
| 自动快照      | 三种触发：① 编辑会话级（停止输入 5 分钟或切换章节时打点，去重压缩）；② 里程碑（手动"存档"，可命名）；③ **AI 改写落库前强制存点** |
| 差异浏览      | 复用 `DiffViewer`，支持任意两版本对比（含跨里程碑）                                          |
| 一键回滚      | 回滚生成新版本而非覆盖，回滚本身可再回滚                                                      |
| 时间机器      | 按时间轴拖动，回看任意时刻的整本作品状态（章节 + 大纲 + 记忆快照）                                      |
| 草稿 / 正典双轨 | 章节区分 `draft` / `canonical` 两态：草稿态自由编辑与 AI 试写，定稿后进入正典并对读者可见（为 E4 发布态铺路）    |
| 保留策略      | 按订阅分层：免费 3 天 / 创作者 90 天 / 专业永久（同时也是订阅提价的权益支撑）                             |

**涉及模块**：`packages/web`（新增 `components/history/`）、`packages/server`（新增 `chapter_versions` 表 + `history_handler.go` + `history_service.go`）、migrations 新增。

**商业价值**：

- 直接消除"不敢用 AI"的心理门槛，提升 AI 调用频次 → 带动 Token 消耗；
- 版本保留时长是最自然的订阅分层维度（用户能理解、能感知、会为了它付费）；
- 是 E4 发布态与 E6 协作的前置依赖。

**验收指标**：AI 改写功能使用率提升 ≥ 30%；因误操作导致的用户投诉归零；创作者档订阅转化率。

### E2 · 伏笔与一致性追踪（P0 · AI 差异化）

**这是 InkBloom 相对所有竞品最可能建立的认知壁垒。**

**现状**：`packages/ai-service/app/knowledge/` 已有实体抽取、关系抽取、一致性检测三个模块，会通过 `KnowledgePanel` 展示冲突提示。

**缺口（K3）**：这三个模块是"点一下、抽一次、显示完就结束"的一次性调用，**没有生命周期**。写长篇最痛的三个问题它一个都没解决：

1. 我在第 3 章埋的伏笔，写到第 40 章忘了收；
2. 这个角色此刻**不应该知道**这件事，但我写的时候忘了；
3. 时间线自相矛盾（去年发生的事写成了上个月）。

橙瓜、灯果、秘塔写作猫、各类 AI 写作工具的通用能力都是"续写/润色"，**没有任何一家做伏笔生命周期管理**。

**方案**：

| 能力     | 说明                                                                                                            |
| ------ | ------------------------------------------------------------------------------------------------------------- |
| 伏笔台账   | 新增 `foreshadows` 表：`(novel_id, 埋设章节, 埋设段落锚点, 描述, 期望回收章节, 状态)`。状态机：`planted → reminded → resolved / abandoned` |
| 自动埋设识别 | 写新章时 AI 自动识别疑似伏笔（悬念句、未解道具、未回答的提问），提示作者"是否登记为伏笔"——**把录入成本从手工降到一次点击**                                           |
| 到期提醒   | 距期望回收章节 ≤ N 章时，在写作侧边栏与大纲面板显示待回收清单；超期未回收的升级为醒目提示                                                               |
| 角色状态快照 | `character_states`：角色在每章结束时的**已知信息集、所在位置、持有物、当前情绪**。写新章时自动校验"这个角色此刻不该知道 X"                                    |
| 时间线校验  | 从正文抽取带时间标记的事件，构建事件时序，检测矛盾（如"三天前"与已写时间轴冲突）                                                                     |
| 主动介入   | 以上检测从"事后点按钮"改为**写作过程中侧边栏实时提示**（可关闭）                                                                           |

**涉及模块**：`packages/ai-service`（`knowledge/` 扩展 + 新增 `foreshadow` 模块 + prompt 模板）、`packages/web`（`KnowledgePanel` 增加"伏笔"与"时间线" Tab、写作侧边栏提示条）、`packages/server`（2 张新表 + handler/service）。

**成本说明**：伏笔校验可复用已有的前情摘要与实体抽取结果，增量 token 消耗可控（估算单次 3k~~6k 输入，约 0.01~~0.02 元/章）；建议打包进订阅权益而非按次计费，避免用户因省钱而关闭核心体验。

**商业价值**：

- 长篇连载作者的**刚需**，是唯一能让用户说出"别的工具没有"的能力；
- 支撑订阅从 10 元提到 29 元档（专业档核心权益）；
- 天然产生"作品越厚、价值越高"的沉没成本锁定。

**验收指标**：长篇作品（≥ 20 章）的作者周留存；伏笔登记率（登记伏笔数 / AI 提示数）；该功能在用户调研中的"不可替代性"评分。

### E3 · 作品数字孪生 + 主动式 AI（P1 · AI 深度）

**现状**：`novel_outline`（大纲）、`novel_memory`（记忆四分组）、`knowledge_nodes`（知识图谱）、`chapters.content`（正文）四份数据各自成岛。前情摘要靠作者手工维护，AI 每次续写都在"重新认识这本书"。

**缺口**：数据是死的，AI 是瞎的。

**方案**：

| 能力     | 说明                                                                             |
| ------ | ------------------------------------------------------------------------------ |
| 作品状态聚合 | 构建可查询的"作品当前状态"：谁在哪、发生了什么、关系如何、未回收伏笔有哪些。作为所有 AI 调用的默认上下文                        |
| 自动前情摘要 | 每完成一章，AI 自动生成/更新前情摘要，替代手工维护。摘要分层（全本摘要 + 近 3 章细摘要），按 token 预算动态拼装               |
| 风格画像   | 从已写正文提取风格特征（平均句长、对话占比、视角、时态、高频词、标点习惯、段落节奏），生成"风格卡"；续写时作为硬约束注入 prompt           |
| 去 AI 味 | 已有右键"去 AI 化"是通用规则，升级为**基于本人历史正文的个性化改写**——学自己的文风，而不是套通用的"像人话"模板                 |
| 主动式介入  | 三类主动提示：① 卡壳检测（同一段落长时间无有效输入）→ 提供三个可能走向；② 偏离大纲（本章内容与大纲要点相似度低于阈值）；③ 人设崩塌（E2 能力复用） |
| 记忆自动归档 | 写完一章后 AI 提议"是否将以下内容存入记忆"（新设定、新角色、新约定），一次点击完成                                   |

**涉及模块**：`packages/ai-service`（新增 `workstate` 聚合模块 + `style` 风格模块 + prompt 模板版本化，复用 v2 已设计的 prompt 版本化机制）、`packages/server`（缓存层，避免每次重算）。

**成本说明**：风格画像与前情摘要均可缓存（变更时才重算），边际 token 成本低；建议在 Token 账单中单列"作品理解"类目，让消耗透明可见。

**商业价值**：把 AI 从"可替代的工具"变成"越用越懂你的伙伴"，直接决定 Token 复购率——这是唯一能持续产生收入的指标。

**验收指标**：AI 生成内容的采纳率（当前无埋点，需先补）；续写结果的"风格相似度"人工盲评；Token 复购率。

### E4 · 阅读器与一键发布（P1 · 增长引擎点火）

**这是把产品从工具变成平台的那一步。**

**现状（K1）**：无阅读器，无发布，无分享。作品出口只有本地文件下载。

**方案**：

| 层        | 能力                                                                                                      |
| -------- | ------------------------------------------------------------------------------------------------------- |
| **发布**   | ① 作品/章节一键发布，生成 H5 作品主页（SEO 友好 + OG 分享卡片）；② 章节定时发布、存稿箱、首发预告；③ 发布态与草稿态分离（依赖 E1 双轨）；④ 可见性控制：公开 / 链接可见 / 私密 |
| **阅读器**  | ① 沉浸式排版（字号、行距、页宽、主题、夜间模式可调并记忆）；② 章节流式翻页 + 目录抽屉；③ 阅读进度云同步（多设备续读）；④ 书签与划线；⑤ 追更订阅（新章发布时站内通知，可选短信/邮件）       |
| **读者账号** | 阅读免登录；互动（评论/投票/打赏）才需轻量注册。降低阅读门槛是流量前提                                                                    |
| **数据回流** | 作者仪表盘新增：追更人数、章节读完率、跳出章节、划线热区、互动分布。这些是作者在其他平台也拿不到的细粒度数据                                                  |

**涉及模块**：`packages/web` 新增 `components/reader/`（阅读器）、`components/publish/`（发布）；`packages/server` 新增 `published_works` / `published_chapters` / `reading_progress` / `reader_follows` 四表 + 对应 handler/service；**发布页为独立静态渲染**（SSR/预渲染以保 SEO，与 SPA 应用分离部署，类似落地页策略）。

**合规前置**：UGC 公开发布须接入现有内容安全网关（`pkg/contentsafety`，已实现）+ 举报入口 + 违法信息处置机制；生成式 AI 内容标识须在发布页显著标注（《生成式人工智能服务管理暂行办法》要求）。

**商业价值**：

- **获客**：每部发布作品都是一个 SEO 长尾入口 + 社交传播节点，获客成本趋近于零；
- **留存**：作者有了"读者在等我更新"的外部约束，留存逻辑从工具变成责任；
- **转化**：读者 → 作者的转化路径天然存在（"我也想写"按钮直连注册）。

**验收指标**：发布作品数 / 活跃作者数（发布渗透率）；阅读端 UV 与自然新增注册占比；分享带来的回流率。

### E5 · 交互式微创作（P2 · 护城河）

**《备忘录》idea 的本体落地：「交互式微创作的小说阅读体验，低消耗的小说微调玩法」。**

关键词是**低消耗**——读者参与创作的成本必须低到"点一下"或"填一个词"，而不是"写一段话"。

**方案**：

| 玩法         | 交互                                                  | 消耗 |
| ---------- | --------------------------------------------------- | -- |
| **段落划线评论** | 选中任意句子即可评论，其他读者可点赞/回复，作者可回复                         | 中  |
| **段落情绪点击** | 段落旁一组情绪图标（燃/刀/甜/谜），点一下即完成反馈，聚合为"章节情绪曲线"             | 极低 |
| **分支投票**   | 作者写出 A/B 两个走向，读者投票，得票高者成为正典，败者进入"平行宇宙"              | 极低 |
| **填空共创**   | 作者在正文中留白（如"来客自称【　　】"），读者投稿候选词，作者采纳后自动填入正文           | 低  |
| **剧情分支树**  | 互动小说模式：章末选择决定下一章走向（进阶玩法，E5 后期）                      | 中  |
| **采纳闭环**   | 读者的评论/投稿被作者"采纳进正文"后，系统署名致谢并通知该读者——**这是让读者留下来的核心机制** | —  |

**关键设计约束**：

1. 所有采纳进正文的操作必须走 E1 的版本历史，可回滚；
2. 采纳需作者确认，**不做自动采纳**（避免作品被污染、规避内容安全责任）；
3. 读者互动数据作为 AI 偏好信号回流 E3（"这一段读者反馈最好/最差"）。

**涉及模块**：`packages/web` 新增 `components/reader/interactions/`；`packages/server` 新增 `interactions` / `interaction_votes` 表 + WS 实时互动推送；与 E4 共用发布态数据。

**商业价值**：

- **这是最难被复制的部分**——竞品能抄编辑器、能抄 AI 动作，抄不走已经形成互动习惯的读者社区；
- 互动行为产生的社交压力（有人评论、有人等我）是最强的留存因子；
- 为 E7 的打赏/分成模型提供场景。

**验收指标**：互动率（有互动行为的阅读会话占比）；读者 → 作者转化率；采纳率（被采纳互动 / 总互动）。

### E6 · 协作与多端（P2–P3 · 扩大场景）

**现状（K7）**：单用户单设备模型，无协作。

**方案**：

| 能力    | 说明                                                                                |
| ----- | --------------------------------------------------------------------------------- |
| 多人合著  | 作品级成员 + 三种角色：`owner`（全部权限）/ `editor`（编辑 + 批注）/ `viewer`（只读 + 评论）。章节级可单独授权         |
| 编辑约稿流 | 编辑下需求卡（选题/要点/字数/截止时间）→ 作者交稿（草稿态）→ 编辑批注（复用现有 `ReviewPanel`）→ 定稿入正典。直接服务自媒体团队与网文工作室 |
| 实时协同  | 不做 OT/CRDT（成本过高），采用**章节级签出锁 + 状态提示**（"XX 正在编辑"），契合长篇创作的低并发场景                      |
| 移动端   | 分两步：① 读者端优先（H5 已由 E4 覆盖，可加壳为小程序）；② 作者端移动端仅做**只读 + 灵感速记**（速记一键归入"灵感素材"记忆分组）        |

**涉及模块**：`packages/server` 新增 `collaborators` / `work_orders` 表 + scope 层扩展（现有 `internal/scope` 已做 user 隔离，需扩展为"用户可见作品集"）；`packages/web` 新增协作管理 UI。

**商业价值**：从个人工具升级为团队工具，**客单价天花板从 10 元/月抬到数十元/月**，且团队付费的流失率远低于个人。

**验收指标**：团队作品占比；团队席位 ARPU；协作场景下的邀请扩散系数（K 因子）。

### E7 · 商业化模型升级（P3 · 换权益结构）

**现状问题**：订阅卖"云同步"（弱需求），AI 卖算力（可替代）。两个乘数都起不来。

**升级后的权益结构**：

| 档位      | 价格     | 核心权益                                                    |
| ------- | ------ | ------------------------------------------------------- |
| **免费**  | 0      | 全部创作功能（含桌面端离线）、本地备份、发布与阅读、**3 天版本历史**、基础 AI（Token 计费）   |
| **创作者** | 10 元/月 | + 云同步跨设备、**90 天版本历史**、伏笔与一致性追踪、读者数据仪表盘、定时发布             |
| **专业**  | 29 元/月 | + **永久版本历史**、风格画像与去 AI 味、主动式 AI、协作席位 ×3、作品数据导出（CSV/API） |

设计原则：**免费档保留完整的"创作 + 发布 + 阅读"能力**（增长引擎必须对所有人生效），订阅只卖"深度与安全感"，不卖"能不能用"。

**新增收入线**：

| 收入线   | 说明                                   | 优先级 |
| ----- | ------------------------------------ | --- |
| 读者打赏  | 章节/作品级打赏，平台抽成；作者提现需实名 + 门槛（合规前置）     | P3  |
| 模板市场  | 人设卡模板、大纲结构模板、Prompt 模板；UGC 上架 + 平台抽成 | P3  |
| 作品推广位 | 站内推荐位（**不做信息流广告**，避免破坏阅读体验）          | P3  |

**关于广告的立场**：阅读端不放第三方广告。体验是 E4/E5 的全部价值所在，广告会直接摧毁飞轮。

**验收指标**：ARPU（目标从当前约 1.6 元/注册用户/月提升）；订阅结构与档位分布；Token 复购率；自然获客占比。

## 8. 风险与应对

| 风险               | 影响                         | 应对                                                                                  |
| ---------------- | -------------------------- | ----------------------------------------------------------------------------------- |
| **阅读端 UGC 合规**   | 公开发布意味着内容安全主体责任，违规内容可能导致下架 | 现有 `pkg/contentsafety` 覆盖文本/图片审核，发布前强制过检；补充举报入口 + 24h 处置机制 + 违法信息留存；生成式 AI 内容标识显著展示 |
| **AI 提示的误报引发反感** | E2/E3 的主动提示若误报率高，会被视为打扰而关闭 | 所有提示可一键关闭且记忆偏好；首期只做高置信度提示（人设矛盾、伏笔超期），卡壳检测等主观提示后置                                    |
| **Token 成本失控**   | E3 的作品状态聚合会推高单次调用输入长度      | 前情摘要分级缓存、风格画像变更才重算；作品状态按 token 预算截断；E3 上线前做成本压测，必要时对超长上下文作品启用分段摘要                   |
| **读者端投入产出不确定**   | E4/E5 是重投入，若作品发布渗透率低则飞轮不转  | 首期只做最小闭环（发布 + 阅读 + 划线评论），用发布渗透率与阅读 UV 两个指标验证后再投 E5                                  |
| **协作的并发复杂度**     | 实时协同（OT/CRDT）成本极高          | 明确不做实时协同，采用章节级签出锁；长篇创作本就是低并发场景，体验损失可忽略                                              |
| **范围蔓延**         | E1–E7 是大量工作，容易全线铺开全线不精     | 严守 P0 → P1 → P2 → P3 的串行纪律；每个阶段设明确的"不达标则不复投"判据                                      |
