# 个人备忘录
> 本项目的 idea

不仅是编辑器，还是小说阅读器：交互式微创作的小说阅读体验，低消耗的小说微调玩法

发现页的内容社区也是产品的一个商业潜力点

自媒体创作模式如何实现常见平台的web自动化起稿呢？

本作品如何去中心化，尽可能减少创作者和读者之间利益互换的损耗，从而吸引创作者自己开拓读者用户，这意味着本作品主要从AI业务和用户的注意力资源上面赚钱，而不是抽成模式

灵感、阅读、获赞代表着人类的智慧价值、注意力价值、认同价值，本作品的盈利建立在这三种价值之上。

要在阅文作家助手之上去思考，才能取得优势

人类可以创作一条故事主线、世界骨架，宣扬特定的主题，但可以呈现多分支，做到千人千面。创作者贡献了智慧价值，读者贡献了注意力和认同，而AI把更多读者纳入同一智慧来源的衍生领域里面去了。AI只是创作者的放大器，并没有自行产生价值的根据，所以如何让创作者选择在这个平台使用AI，就是核心问题。

既然文本被AI解决了，那么小说创作不应该升维到图创作，或者流创作吗？

是你给了创作Agent的端到端测试录E2E点子让它写的吗 如何让AI创作都有这样的质量？因此书的创意可以用ai展开 AI起稿页增加一栏创作意图 人类只要定受众 定创作意图 标题和创意也可以由ai给出

做测试一定要按照最小 tokens 消耗原则来 别把我的 tokens 花光了

考虑世界线分支怎么做
比较采用git分支原理来支撑整个世界树的存储（每节点存git的快照 获取内容时借助git推断节点内容） 和 采用单点文章存储（每节点存一个文章）的服务器开销
全量存储配合指针模型
git 给世界线的是“分支语义”，不是“存储格式”。语义（不可变快照、指针、checkout、hash 去重）我们全拿了；格式（CAS、推断读取）对小说文本这种“极小数据 + 读密集”的负载，只有成本没有收益。

文章创作时 是否有必要对单文章实施真正的git管理 尤其是存在ai反复生成改写+变动即存的情况下 如何做浏览器快存+提交服务器降频应对变动既存
三层管道：IndexedDB 本地 ≤2 次/秒（毫秒级，无网络）；服务器提交压缩到活跃期 5-10 次/分钟；L3 快照再收敛到 ~1 行/分钟。两小时写作会话：请求几百个、版本行几十条、里程碑另计——读者端零影响。
AI 场景：服务器历史的计量单位从“AI 迭代”变成“作者采纳”。反复生成改写不再产生任何服务器写入，直到作者点采纳——这才是对“AI 反复生成 + 变动即存”的真正降频。

把本站头部置于最高层级 实现最大化按钮始终控制当前聚焦窗口的最大化 

3种AI记忆软闸：
AI全局忽略，打开后向AI说明忽略此记忆，除非人类指令明确提及，默认关闭；
AI限制可见，改为单选模块，打开后向AI说明选中章节解锁，以前视为不可见，绝对不能剧透，提前显露，但是允许以伏笔或隐晦的线索出现，默认关闭；
AI局部可见，多选模块，打开后向AI说明选中章节视为可见，其他章节视为不可见，绝对不能剧透，提前暴露，但是允许以伏笔或隐晦的线索出现，默认关闭；
3种AI记忆硬闸：
AI全局禁用，不向AI注入该条目，默认关闭；
AI限制禁用，单选模块，选中章节以及以后向AI注入该条目，默认关闭；
AI局部禁用，多选模块，选中章节向AI注入该条目，默认关闭；
