# 核心施工记录 2026-09-04：写作状态收敛两态 + 发布状态系统管理

## 需求

- 写作状态管理合并为 2 态：写作中（drafting）/ 已完成（done）。
- 节点页（大纲节点卡）把状态标签替换成 2 态切换按钮。
- 该切换按钮同时加到编辑器工具栏「发布」按钮左侧，用于切换当前章节状态。
- 发布状态由系统管理：章节发布成功后自动同步为「已发布（published）」，用户不可手改。

## 方案

写作状态两态（drafting/done）由用户切换；`published` 作为系统写入的第三态复用大纲节点
JSON 通道（无需新增后端端点）。legacy `planned`（未开始）读取时收敛为 drafting，写回后自然淘汰。

## 补充 3：身份如实化下沉到 ai-service 层，覆盖全部对话端点（同日）

### 问题

用户反馈「调用 api 还是没有返回模型真名」。上轮身份指令只加在 Go 侧
`agent_service.go` 的 Agent 路径，且该注入代码又被外部回退。排查发现：

- 前端 AI 对话面板 `sendMessage` 实际走 `agentChat → POST /api/v1/agent/chat →
  Go AgentService → ai-service /api/agent/chat`；
- 而 `/api/chat/stream|complete|inline|rewrite` 等普通对话端点、以及
  `/api/agent/chat` 端点，system prompt 里都没有「如实回答原生名字」的指令；
- `agentSystemPrompt` 只说「你是 InkBloom 的创作 Agent」，模型被问「你是谁」时
  会答产品名「InkBloom 创作 Agent」或幻觉成 GPT，而非原生模型名。

### 修复：身份注入统一收敛到 ai-service HTTP 层

`packages/ai-service/app/main.py` 新增 `_IDENTITY_HINT` 与幂等辅助函数
`_with_identity(messages, model)`——把「你由模型 {model} 驱动；被问名字时如实以
原生名称回答（GLM/DeepSeek），不要自称 GPT/ChatGPT，不要伪装」追加到首条 system
消息末尾（无 system 时插入一条）。应用到**全部 5 个作者可对话端点**：

- `/api/chat/stream`、`/api/chat/complete`、`/api/chat/inline`、`/api/chat/rewrite`、
  `/api/agent/chat`。

知识抽取（entity/relation/consistency/foreshadow）、图像 prompt、AI action 场景生成等
**机器调用端点不经此层**（它们要求严格 JSON、从不被问身份），避免污染输出。

`packages/server/internal/service/agent_service.go`：移除（此前被回退的）Go 侧重复注入，
改为注释说明「身份由 ai-service `_with_identity` 集中注入，勿在此重复」——单一事实来源，
model 名以 ai-service 解析值（含 default 回退）为准。

### 顺带修复：rewrite 场景模型未透传

`packages/web/src/stores/ai-store.ts` `triggerRewrite` 调用 `streamRewrite` 时漏传
model（inline 已传）。补 `resolveSceneModel('rewrite')`，使改写跟随所选模型——
这也是「模型切换未生效」的一个实例。

### 验证（重启 ai+go 后直测 ai-service，含真实链路人设）

- `/api/chat/complete`：`glm-4.5-air` → 「我是GLM模型。」；`deepseek-chat` →
  「我是由深度求索（DeepSeek）公司开发的DeepSeek模型。」✓
- `/api/agent/chat`（带「你是 InkBloom 创作 Agent」人设，模拟前端真实链路）：
  问「你叫什么名字？你是 GPT 吗？」→ 「我是GLM模型，不是GPT。」✓
- 幂等：`_IDENTITY_HINT` 已存在时不重复追加。
- `python -c ast.parse`、`go build ./...`、`tsc --noEmit` 通过。
- 注：GLM-4.5 默认动态思考，`max_tokens` 过小（如 60）会被思考耗尽导致 content 空，
  实测需 ≥ 数百；生产对话链路 max_tokens=2048 不受影响。
- 过程遇到 go server 启动 `nats: filtered consumer not unique`（已知问题），
  `docker restart inkbloom-nats` 后恢复。

## 补充 5：修复概览页与节点页"消失"（currentNovel 恢复时机 + dev server 模块污染）

### 现象

选中作品后中央不显示作品概览页（退化为"选择或创建一个章节开始写作"欢迎页），
左侧大纲/记忆页只剩"先选择一部作品"空态；两者同时消失。

### 根因（两层）

1. **真实根因（代码缺陷）**：作品列表加载与 `currentNovel` 恢复逻辑只挂在
   `NovelList`（作品库 Tab）的挂载 effect 里。刷新页面时若 `leftTab` 持久化为
   `outline`/`memory`，NovelList 不挂载 → `fetchNovels` 永不执行 →
   `inkbloom:currentNovelId` 恢复分支永不触发 → `currentNovel === null`。
   概览页（EditorArea 的 `currentNovel` 分支）与节点页（OutlinePanel）同时失效。
2. **dev 环境叠加因素**：长期运行的 vite dev server 累积多个 HMR 世代，
   模块图把 `novel-store.ts` 以 3 个 URL（两个 `?t=` 时间戳副本 + 干净副本）
   重复加载，同页出现多个 zustand 实例，组件间状态互不相通，症状进一步加重。
   （生产构建/重启后不存在此问题。）

### 修复

- `packages/web/src/App.tsx`：`AuthenticatedApp` 挂载 effect 增加应用级
  `useNovelStore.getState().fetchNovels()`——启动即拉取作品列表并按
  `inkbloom:currentNovelId` 恢复选中作品，不再依赖作品库 Tab 是否挂载；
  NovelList 自身的刷新 effect 保留（恢复分支有 `!currentNovel` 守卫，幂等）。
- 重启 vite dev server 清除 HMR 污染的模块图（重载后 novel-store 仅加载一次）。

### 验证（浏览器实测）

- 模拟登录 → 刷新（leftTab 停留在大纲）→ 概览页恢复（标题/简介/发布管理/
  读者数据/世界线入口齐全）、大纲节点树与两态状态按钮恢复；
- 点击节点卡 → 中央标签页节点编辑器正常打开（状态/扩写成稿/保存）；
- `performance` 资源面板确认 `novel-store.ts` 全页仅一次加载；
- `pnpm exec tsc --noEmit` 通过。

## 补充 7：章节发布系统顺序显示修复（"第0章/第19章"错误编号根治）

### 现象与根因

发布管理 / 读者数据看板出现「第19章 / 第20章 / 第0章」等错误编号。数据实查坐实三层根因：

1. **position 语义错位**：`chapters.position` 是混用自增（`GetMaxPosition+1`）与
   0-based 插入索引的内部排序键，有洞（0,1,10,11,13,21-27）、有重复，与大纲顺序
   完全脱节；而 WorkStatsPanel「第{position}章」、发布 milestone label
   「第{position}章」都拿它当人类可读编号 → 第0章 / 第19章。
2. **幻影绑定**：大纲节点 `chapter_id=1788521517566` 指向不存在的章节——前端
   DEV_MOCK 建章失败时生成 `Date.now()` 假 id 又 `saveOutline` 写回后端。
3. **重复章节**：「审判之后」有 3 份（79/143/144），`handleWriteDraft` 无条件
   `createChapter` 造成同名重复；`bindChaptersToOutline` 同名节点已绑时追加新要点。

### 修复

**后端（数据层为根，显示层为表）**
- `novel_doc_service.go`：
  - 新增 `sanitizeOutlineBindings`（清除幻影 + 重复 chapter_id，一节点一章节，
    返回大纲序 bound ids）、`resyncChapterPositionsToOutline`（position 重写为
    大纲序，已一致则跳过不churn updated_at）、`SyncOutlineChapterOrder`
    （web 保存后独立调用：净化 + 落盘 + 重排）；
  - `MigrateCleanupOrphanChapters` 复用 sanitize，并在删孤儿后 resync 全部作品
    position 为大纲序（启动幂等运行）。
- `novel_doc_handler.go`：PUT /outline 提交后调用 `SyncOutlineChapterOrder`
  （best-effort）。**关键**：sanitize/resync 必须与 `UpdateOutline` 分离——整本
  版本 restore 在事务内写大纲，若在 UpdateOutline 里嵌套 chapterRepo 事务会与
  SQLite 共享缓存写锁死锁（曾致 restore 测试 38s 超时，已修复并回归）。
