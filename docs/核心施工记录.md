## 2026-08-31 · A22 会话持久化（T2）

**做了什么**：把 refresh token 从 kvstore（Redis/内存）迁移到持久化的 `user_sessions` 表。

**为什么**：原实现 refresh token 只存 kvstore——云端存 Redis、桌面本地模式存内存 kv。桌面端重启即掉登录，「3 端在线 + 踢最早」无落点，设备管理页无法列出设备（方案 v3 缺口 K5）。

**实现了什么**：
1. 新增 `user_sessions` 表（model/repo/repository 三件套），字段含 jti（唯一）、设备名/类型/IP、last_active_at、expires_at。
2. `issueTokens` 改写：签发时落一条 session 行（滑动 30 天窗口 = refresh TTL），并强制「单账号最多 3 会话」，超出踢最早活跃。
3. `Refresh` 改写：按 jti 原子消费旧 session（单条 DELETE，RowsAffected 判重，杜绝并发双刷），携带旧设备元数据签发新 session（避免刷新被误判成新设备撞 3 端上限）。
4. `Logout` 改写：单会话吊销走 `Consume(jti)`，全量下线走 `DeleteByUser`。
5. 新增 `GET /api/v1/auth/sessions`、`DELETE /api/v1/auth/sessions/:id` 设备管理端点；设备类型由 User-Agent 识别（Electron→桌面、mobile 关键词→移动、其余→web）。
6. 短信验证码仍走 kvstore（无需设备维度），不受影响。

**取舍**：保留 kvstore 仅用于短信验证码与限流；refresh 会话全量迁表。local 模式 SQLite 持久化，云端 PG 持久化，双模式行为一致。设备管理前端 UI 暂缓，后端端点已就绪。

**验收**：`go build ./... && go vet ./... && go test ./...` 全绿。

## 2026-08-31 · A23 阅读数据回流 + 追更计数修复

**做了什么**：① 作者侧新增阅读数据端点与面板；② 修复追更计数膨胀 bug。

**为什么**：飞轮「创作→发布→阅读→互动→反哺」缺最后一段——作者发布了作品却看不到任何读者数据（方案 v3 判断三：没有反馈闭环）。同时 `Follow` 无条件 `IncFollowCount`，重复点追更会让计数虚高。

**实现了什么**：
1. 新增 `GET /api/v1/publish/works/:wid/stats`，返回追更人数、累计阅读人数、每章当前阅读人数漏斗。
2. 仓储层新增 `ReadingDistribution`（按 chapter 聚合最新进度）与 `DistinctReaders`（COUNT DISTINCT user_id）。
3. 前端 `WorkStatsPanel` 组件 + 接入发布弹窗（PublishModal），展示追更/阅读指标卡与每章阅读漏斗条。
4. `Follow`/`Unfollow` 改为幂等：已关注则不重复计数、未关注则不重复扣减；`UpsertFollow` 冲突更新不再覆盖 `created_at`（原实现会把关注时间重置为零值）。

**取舍**：reading_progress 只存读者「最后位置」，每章人数 = 读者最后停留点，是对读完率的诚实近似；要精确到「每章完成率」需另加逐章进度事件表（列入后续 E5 埋点），本期不引入。

**验收**：`go build ./...`、`pnpm build` 全绿。

## 2026-08-31 · E5 交互式微创作（A28+A29）——产品护城河

**做了什么**：在公开阅读器上落地上层读者互动：段落情绪点击 + 划线评论 + 点赞 + 作者采纳。

**为什么**：这是《备忘录》idea 本体（「交互式微创作的小说阅读体验，低消耗的小说微调玩法」）与方案 v3 判断里唯一「抄不走」的护城河。E4 已把读者端建成，但仍是「只读孤岛」——没有互动就没有留存与作者反馈闭环。

**实现了什么**：
1. 数据模型：`interactions`（类型 comment/mood、block_index 锚定段落、payload 类型化、状态 pending/adopted/hidden、like_count）+ `interaction_votes`（user×interaction 唯一，点赞 toggle）。
2. 后端：`InteractionService` + `InteractionHandler`，端点 `GET/POST /read/chapters/:pid/interactions`、`POST /interactions/:iid/like`、`DELETE /interactions/:iid`、`POST /publish/interactions/:iid/adopt`。评论过内容安全（C12），采纳仅作者可操作（404 防探测）。
3. 前端：阅读器段落悬停浮出情绪条（燃/刀/甜/谜，一次点击即反馈）；选中文本浮出「划线评论」；右侧互动侧栏（情绪汇总、评论列表、点赞、作者采纳/隐藏、评论输入框）。

**取舍**：首期只做「划线评论 + 情绪点击 + 采纳」最小闭环（方案 Q4），分支投票/填空共创后置；「采纳」先落地为作者认可置态（已采纳徽标），自动填回正文的 `fill` 玩法待后续版本；读者被采纳后的 WS 站内通知待补（复用现有 WS Hub）。

**验收**：`go build ./...`、`go vet ./...`、`pnpm build` 全绿。

## 2026-08-31 · 修复：发布弹窗内容被遮挡（fixed 弹窗被困 containing block）

**现象**：文章发布窗口（PublishModal）打开后内容被遮挡/错位。

**根因**：代码库存在两套弹窗写法——`common/Modal.tsx`（portal 到 body，正确）与手写 `fixed inset-0` 弹窗（错误）。手写弹窗只要挂在带 `backdrop-filter`/`transform`/`filter` 的祖先节点下，该祖先就会成为 fixed 后代的 containing block，`inset-0` 不再覆盖视口，弹窗被压缩进祖先盒子里、内容被编辑器其它表面遮挡。PublishModal 恰好挂在 Toolbar 内，而 Toolbar 根节点带 `backdrop-blur`；`glass-panel`（common Modal 面板）同样带 `backdrop-filter: blur(16px)`，会殃及嵌套其中的手写 fixed 层（版本对比 DiffViewer）。

**修复**（全部改为 portal 到 `document.body`，与 common/Modal 策略一致）：
1. `PublishModal` —— 根节点包 `createPortal(document.body)`。
2. `DiffViewer` —— 根节点 portal（同时修复编辑器内与版本对比弹窗内两种使用场景）。
3. `VersionCompare` 加载遮罩 —— portal。

**为什么“总是”出这类问题**：手写 fixed 弹窗没有强制 portal 的约定，只要有人在带 backdrop-filter/transform 的容器里再挂一个手写弹窗就会复发。已在此三处注释中写明原因；后续新增弹窗应一律走 `common/Modal` 或自行 portal。

**验收**：`pnpm build` 全绿。

## 2026-08-31 · A31 章节情绪曲线（作者侧读者情绪反馈）

**做了什么**：把 E5 的段落情绪点击数据回传给作者——发布面板中每章可展开查看「情绪曲线」。

**为什么**：E5 收集了读者的燃/刀/甜/谜情绪，但作者看不到；这是飞轮「互动数据 → 反哺作者」的最后一公里，也是其他平台拿不到的细粒度反馈。

**实现了什么**：
1. 后端 `GET /api/v1/publish/chapters/:pid/emotions`（作者专属，404 防探测）：按 block_index 聚合情绪互动，返回每段四情绪计数 + 全章汇总。
2. `PublishService` 注入 `interactionRepo`，聚合逻辑在 service 层（JSON payload 解析 + 排序）。
3. 前端 `WorkStatsPanel` 章节行改为可展开：点击拉取情绪数据，SVG 折线图（四色：燃橙/刀红/甜粉/谜紫）+ 汇总 chips。

**取舍**：情绪曲线按「有情绪的 block」等距分布 X 轴（不做整章逐段铺开，避免无数据段拉平曲线）；仅作者可见。

**验收**：`go build/vet`、`pnpm build` 全绿。

## 2026-08-31 · A30 用量日聚合（T3）+ ai-service 依赖清单修复

**做了什么**：① 新增 `token_usage_daily` 日聚合表 + 写穿 + 查询端点；② 补齐 ai-service 缺失的依赖声明。

**为什么**：运营后台与用量面板要展示趋势，只能实时扫 append-only 的 `token_ledger`（数据量大后必然变慢）；且启动全部服务时发现 ai-service 的 `requirements.txt` 漏了 `httpx`/`pillow`（多 agent 施工遗留，缺其一无法启动，Docker 镜像同样会挂）。

**实现了什么**：
1. `token_usage_daily` 表（user_id+date 唯一），`text_units`/`image_count`/`image_units` 三计数。
2. `TokenService.Consume` 扣减成功后写穿日聚合（best-effort，失败仅 WARN 不阻断主链路）；`image_gen` 计入 image 计数，其余计 text。
3. 新增 `GET /api/v1/token/usage/daily?days=30`，读聚合表按日返回（比扫 ledger 快）。
4. `requirements.txt` 补 `httpx`、`pillow`。

**取舍**：日聚合按 `Asia/Shanghai` 时区切日（与现有 stats 一致）；`/token/stats` 仍读 ledger（其 day/week/month 三粒度与日表不同，切换属后续优化，待日表积累足够历史后再切）。写穿失败靠后续补跑可恢复，不引入定时回填任务。

**验收**：`go build/vet/test`、AI 服务 `python -m app.main` 启动、`/health` 返回 ok。
